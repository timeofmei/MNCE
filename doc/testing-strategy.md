# 测试策略

## 适用范围

本文是 MNCE 自动测试与里程碑验证的权威文档。各里程碑文档只描述该阶段需要验证的具体工作流和验收结果，不重复定义通用测试规则。

## 里程碑测试要求

从后续里程碑开始，每个里程碑都必须根据其变更范围提供分层自动测试：

- 领域逻辑、持久化和外部边界使用确定性的单元测试或组件测试。
- 每个新增或发生实质变化的用户工作流至少包含一条自动化 GUI 端到端测试。
- 修复用户可见的行为缺陷时，应在适合的测试层增加回归测试。
- CTest 必须能够发现并运行里程碑新增的全部自动测试。

如果一个里程碑不包含可交互的用户工作流，例如仅调整构建或内部依赖，则可以不增加 GUI 端到端测试，但里程碑文档必须说明原因及替代验证方式。

## GUI 端到端测试边界

GUI 端到端测试应从窗口级入口驱动真实界面控件，并跨越该工作流实际使用的应用服务和临时数据库。测试应使用 Qt Test 模拟点击、选择和输入，并等待异步任务产生可观察结果，而不是直接调用本应由用户操作触发的私有实现。

测试至少验证工作流的用户可见结果，并在必要时验证持久化结果。例如：

- 添加媒体后列表出现对应记录。
- 切换目标语言后只显示对应内容空间。
- 文件缺失、重新定位、删除或后台任务完成后，界面状态与数据库一致。
- 应用关闭并重新创建窗口后，要求持久化的状态能够恢复。

端到端测试不直接自动操作操作系统原生文件选择器或原生消息框。此类边界应通过可替换接口注入：生产环境使用原生实现，测试使用返回预定结果并记录调用的替身。测试替身只替换操作系统交互，不替换被测的领域服务、文件处理或持久化链路。

## 隔离与确定性

自动测试必须：

- 使用临时目录、临时 SQLite 数据库、临时设置文件和运行时生成的小文件。
- 不访问真实用户目录、`local-data/`、网络、音频设备、GPU 或大型 Whisper 模型。
- 不依赖测试执行顺序，也不共享可变数据库或设置状态。
- 对后台任务使用有界等待和可观察完成条件，不使用任意时长的休眠代替同步。
- 在 Debug 和 Release 构建中运行，并保持无新增编译器警告。

## 人工验证

自动 GUI 测试主要验证行为，不能完全替代人工视觉检查。每个包含界面变化的里程碑仍应进行一次简短手动检查，至少关注：

- 常用窗口尺寸下的布局、文字截断和控件重叠。
- Windows 基线环境下的焦点、选中、禁用和错误状态。
- 高 DPI 或显示缩放下的可读性。
- 原生文件选择器和消息框的实际交互。

如果后续引入稳定的截图基线和跨平台执行环境，可以增加视觉回归测试；在此之前，不把像素级截图比较作为完成里程碑的必要条件。

## 里程碑文档写法

新里程碑的“测试”章节应链接本文，并列出该里程碑必须覆盖的具体端到端工作流。验收标准应明确 CTest、Debug/Release 构建以及必要的人工界面检查，不再复制本文的通用约束。
